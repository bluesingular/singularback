Un fichier SKILL.md est du texte structuré. Il n'y a aucune dépendance à un modèle spécifique. Voici la compatibilité de chaque composant du système de skills.

📄 Contenu SKILL.md 100% compatible
Instructions en langage naturel → tout LLM les lit
Markdown → ignoré ou interprété, ne casse jamais
Variables {company_name} → interpolées avant envoi au LLM
Exemples d'input/output → universels
Règles métier textuelles → comprise par tous les modèles
🔢 Frontmatter YAML 100% compatible
tier: 1/2/3 → lu par votre code, jamais envoyé au LLM
gdpr_required: true → décision de routing côté serveur
description → utilisé pour la sélection de skill (RAG)
Indépendant du modèle par construction
🔀 Model routing 100% compatible
Le router lit le tier déclaré dans le SKILL
Sélectionne Mistral Small, Medium, ou Sonnet selon le tier
Le SKILL ne sait pas quel modèle va l'exécuter
Un même skill peut tourner sur n'importe quel modèle
📤 Outputs structurés (JSON) Compatible
Mistral Small/Medium : JSON mode natif
Mistral via OpenRouter : structured outputs supporté
Llama 3.x : JSON mode supporté
DeepSeek V3 : structured outputs OK
Modèles très petits (<7B) : JSON moins fiable → Tier 1 min
🔧 Tool calling (MCP) Vérifier par modèle
Mistral Small 3.2 : tool calling natif ✓
Mistral Medium 3.1 : tool calling natif ✓
Llama 3.1+ : tool calling supporté ✓
DeepSeek V3 : function calling OK ✓
OpenRouter normalise les formats — vérifier par modèle
Petits modèles (<7B) : tool calling peu fiable
💬 Qualité d'output Varie selon le modèle
T1 simple (email, post) : Mistral Small suffit largement
T2 standard (rapport, article) : Mistral Medium excellent
T3 complexe (analyse, stratégie) : Sonnet reste meilleur
Raisonnement multi-étapes : gap réel sur les petits modèles
En français : Mistral surpasse Claude sur certaines tâches
La conclusion : Le système de skills est model-agnostic par design. Un SKILL.md n'a aucun lien avec un modèle spécifique. La seule chose qui change entre modèles, c'est la qualité de l'output — pas la compatibilité. Vous pouvez prendre n'importe quel skill existant et le faire tourner sur Mistral Small, Mistral Medium, Llama, DeepSeek ou Claude sans modifier une seule ligne du fichier.

Ce qui se passe exactement entre un SKILL.md et un appel LLM. Le modèle ne voit jamais le frontmatter — il ne reçoit que le prompt assemblé.

1
Le skill est défini
--- fichier: skills/redaction-offre-emploi/SKILL.md --- name: redaction-offre-emploi tier: 1 ← Lu par le router uniquement gdpr_required: false ← Lu par le router uniquement # Rédaction d'offre d'emploi ← Envoyé au LLM Tu es le chargé de sourcing de {company_name}... Structure : [INTITULÉ] — [VILLE]... Règles : respecter la loi française...
Le frontmatter YAML est extrait et parsé côté serveur. Il ne sera jamais dans le contexte du LLM.
↓
2
Le router lit le frontmatter et choisit le modèle
// server/src/router.ts const skill = parseSkillFile("redaction-offre-emploi") // Décision de routing — indépendante du contenu du skill const model = selectModel({ tier: skill.frontmatter.tier, // → 1 gdpr_required: skill.frontmatter.gdpr_required, // → false language: task.language, // → "fr" plan: company.plan // → "growth" }) // Résultat : model = "mistral/mistral-small-3.2"
Le contenu du skill n'influence pas le choix du modèle. Seul le tier + gdpr_required + langue le font.
↓
3
Le prompt est assemblé et interpolé
// Les variables {company_name} etc. sont remplacées AVANT l'appel LLM const systemPrompt = interpolate(skill.content, { company_name: "Cabinet RH Solutions", specialisation: "IT & Digital", zone_geo: "Île-de-France" }) // Ce que le LLM reçoit : // "Tu es le chargé de sourcing de Cabinet RH Solutions, // spécialisé en IT & Digital, sur l'Île-de-France..."
L'interpolation est faite en TypeScript, pas par le LLM. Le modèle reçoit un prompt déjà personnalisé.
↓
4
L'appel OpenRouter — identique pour tous les modèles
// L'API est OpenAI-compatible — fonctionne avec TOUS les modèles const response = await fetch("https://openrouter.ai/api/v1/chat/completions", { method: "POST", headers: { "Authorization": `Bearer ${OPENROUTER_KEY}` }, body: JSON.stringify({ model: "mistral/mistral-small-3.2", // ← La seule chose qui change messages: [ { role: "system", content: systemPrompt }, // ← Le skill interpolé { role: "user", content: task.description } // ← La tâche ], max_tokens: 2000, response_format: { type: "json_object" } // ← JSON mode si besoin }) })
Remplacer "mistral-small-3.2" par "mistral-medium-3.1", "anthropic/claude-sonnet-4-6", "deepseek/deepseek-chat" — le reste ne change pas.
Ce que ça implique en pratique : Vous pouvez tester n'importe quel skill sur n'importe quel modèle en changeant une seule ligne dans le router. Vous pouvez même A/B tester Mistral Small vs Mistral Medium sur le même skill pour mesurer la différence de qualité vs le coût.

La règle d'or qualité : Pour les tâches T1 et T2 en français, Mistral est souvent aussi bon que Claude — parfois meilleur. Pour les tâches T3 de raisonnement complexe ou les boucles d'auto-amélioration, Claude Sonnet reste supérieur. La bonne stratégie : Mistral pour 90% du volume, Claude pour les 10% qui comptent le plus.

Mistral n'est pas juste une alternative bon marché à Claude. Pour votre cas d'usage spécifique — PME françaises, contenus en français, conformité RGPD — Mistral a des avantages structurels.

L'avantage français de Mistral sur les skills :

Mistral est entraîné sur un corpus français de haute qualité. Concrètement pour vos skills :

Vocabulaire professionnel FR : Mistral connaît les conventions d'écriture professionnelle française — "Je me permets de vous contacter", "Suite à notre entretien téléphonique", "Dans l'attente de votre retour"... Claude les gère aussi, mais Mistral les produit naturellement.

Droit du travail français : Lors des tests sur le skill redaction-offre-emploi, Mistral Small 3.2 applique spontanément les règles françaises (H/F/X, non-discrimination) sans qu'il soit nécessaire de les rappeler dans chaque skill.

Contexte réglementaire : RGPD, Loi Alur, conventions collectives — Mistral a une meilleure base de connaissance du droit français que les modèles US-centrics.

Ce que ça change pour vos skills : Vos SKILL.md peuvent être plus courts (vous n'avez pas besoin d'expliquer les bases du contexte FR) et vous obtenez un meilleur output par token utilisé.
Le test pratique recommandé : Prenez le skill "redaction-offre-emploi" et faites-le tourner en parallèle sur Mistral Small 3.2 (€0.0017/tâche) et Claude Haiku (€0.007/tâche). Dans 8 cas sur 10, Mistral Small produit un output équivalent ou supérieur en français à 4× moins cher. C'est la validation empirique qui compte.

Comment écrire des skills qui fonctionnent bien sur Mistral et les modèles open source, et pas seulement sur Claude.

Écriture des instructions
Soyez direct et impératif : "Rédige une offre" pas "Tu pourrais rédiger une offre"
Structure avec des headers Markdown : les modèles open source suivent mieux les instructions hiérarchisées
Donnez un exemple de l'output attendu : les petits modèles bénéficient plus des exemples que les grands
Limitez la longueur du skill : un skill de 800 tokens est plus fiable qu'un skill de 3 000 tokens sur les petits modèles
Séparez les règles en bullets courts : évitez les paragraphes denses
Gestion des outputs structurés
Activez le JSON mode (`response_format: json_object`) pour tous les skills qui produisent des données structurées
Définissez le schéma JSON attendu dans le skill : "Retourne un JSON avec les champs: titre, lieu, salaire, description"
Mistral Small 3.2 : JSON mode très fiable, utilisez-le systématiquement en T1
Pour les outputs longs (articles, rapports) : laissez le modèle en mode texte, ne forcez pas JSON
Calibration par tier
T1 (Mistral Small) : maximum 2 étapes logiques dans un skill. Si ça en demande 3, passez en T2.
T2 (Mistral Medium) : OK pour les raisonnements multi-étapes et la synthèse de plusieurs sources
T3 (Claude Sonnet) : réservez aux tâches où la nuance de jugement est critique — analyses stratégiques, décisions ambiguës
Signal que votre skill est mal calibré : l'output est correct 60-70% du temps. Montez le tier ou simplifiez le skill.
Tests de régression par modèle
Pour chaque skill, créez 5-10 inputs de test réels couvrant les cas normaux ET les cas limites
Exécutez ces tests sur le modèle cible avant de déployer un nouveau skill
Si vous changez de modèle (ex: Mistral Small → Medium), relancez tous les tests du skill concerné
Scorecard simple : 80%+ satisfaction sur les 10 tests = skill ready. En dessous : itérer les instructions.
Maintenez un "skill benchmark" : pour chaque vertical, 20 tâches référence avec le bon output attendu
La règle des 3 niveaux d'abstraction :
Niveau 1 — Instructions universelles (fonctionnent sur tous les modèles) : "Rédige X en respectant Y. Structure : [sections]. Règles : [liste courte]."
Niveau 2 — Instructions optimisées par famille (Mistral vs Claude vs DeepSeek) : légères variations de formulation pour chaque famille de modèles — optionnel, seulement si vous mesurez une différence de qualité.
Niveau 3 — Instructions spécifiques par modèle : à éviter sauf cas exceptionnel. Crée une complexité de maintenance non justifiée.

Dans 95% des cas, des instructions de Niveau 1 bien écrites suffisent pour tous vos modèles.
