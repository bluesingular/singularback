// The vibe coding philosophy
You are the architect. Claude Code is the engineer.

Vibe coding is not "let the AI do everything and hope." It's a specific workflow: you hold the architecture in your head, you write the prompts precisely, you review every output before it hits disk, and you run the tests before you move on. Claude Code will write 10,000 lines of correct TypeScript. Your job is knowing which 10,000 lines to ask for, in which order, and what "correct" means for each one.

The spec files are your weapon. Every prompt references TECHNICAL_SPEC_v2.md section and page. You never ask Claude Code to invent architecture — you ask it to implement what is already designed.

🚨 Rules of vibe coding

Non-negotiable. Violating any of these will cost you more time than it saves.

Never prompt without a spec reference

Every Claude Code prompt must cite the spec. "Implement X" is bad. "Implement the HeartbeatWorker from TECHNICAL_SPEC_v2.md Module 1, section 'Workers'" is good. The spec is the ground truth — not Claude Code's interpretation.

Review every file before it hits disk

Use Claude Code's review mode: claude --review shows diffs before writing. Never let Claude Code write directly without seeing what it's doing. One bad migration file can cost 2 hours to fix.

One module per session, tests before next

Never start M2 until M1's tests pass. Context drift between modules is real — Claude Code loses coherence across long sessions. Fresh session per module, spec re-read at the start.

The GDPR rule is a code test, not a review

After M3, run: yarn test --grep "GDPR routing" before every commit. This test must never fail. If Claude Code changes the router, it must not break GDPR enforcement.

Commit after every passing module

One commit per module, passing tests, descriptive message. This gives you rollback points at every step. If M5 breaks something, git revert to M4 cleanly.

Keep a session log

After each Claude Code session, write 3 lines in a DEVLOG.md: what was built, what test passed, what's next. This is your continuity across sessions — Claude Code doesn't remember, but you do.

Never let Claude Code touch migrations

Ask Claude Code to generate the migration SQL. You run drizzle-kit push yourself. Never let it auto-migrate in a session without your explicit review of every SQL statement.

Split large modules into 3 prompts

Module 4 (Integration Hub) is complex. Split into: (1) schema + vault, (2) MCP router, (3) webhook handler. Each prompt must be under ~500 words. Long prompts → context overflow → drift.

💀 Traps that will cost you days

Every one of these has happened to someone building this kind of system.

🪤
Asking Claude Code to "just fix it" without spec reference

When a test fails, the temptation is to paste the error and say "fix this". Claude Code will fix it in a way that violates the spec. Always say: "Fix this bug while respecting TECHNICAL_SPEC_v2.md Module N constraints."

Always reference the spec even for bugfixes
🪤
Running migrations without reviewing the SQL

Claude Code might generate a migration that drops a column, changes a type, or adds a constraint that breaks existing data. Every migration SQL must be read line by line before running drizzle-kit push.

Read every SQL statement in every migration file before executing
🪤
Long Claude Code sessions (context drift)

After 2+ hours in a session, Claude Code starts making choices that contradict earlier decisions. The context window fills and it "forgets" constraints. Maximum 90 minutes per session. Fresh session for each new module.

1 module = 1 session. Never cross module boundaries in one session.
🪤
Skipping the idempotency tests for BullMQ workers

BullMQ delivers at-least-once. If your heartbeat worker isn't idempotent, you'll get duplicate tasks, duplicate emails, duplicate memory entries. This corruption is hard to clean up at scale. Idempotency tests before every worker ships.

Write the idempotency test first, then implement the worker
🪤
Building UI before the API is tested

The UI depends on 9 API endpoints. If those endpoints change shape, the UI breaks. Every API route must be tested with Insomnia before building the UI component that consumes it.

API contract first, UI second. Document the contract in a routes.md file.
🪤
The 20-minute test failure

You build the Pack P1 wizard, it works perfectly for you. You give it to a non-technical person and they spend 20 minutes on step 2. Run the 20-minute test with a real non-technical person before claiming Pack P1 is done. Every friction point they hit is a bug.

Test with your least-technical friend/family member, not yourself
